# Спецификация реализации онлайн-этапа: кейс 4

Версия 1.0, 16.11.2026. Согласовано Codex и pi после взаимного ревью.
Основания: [решения и обоснования](ARCHITECTURE.md), [карточка кейса](4keys.pdf), [контракт стенда](team22_data_org/README.md).

Этот документ задаёт реализацию бэкенда онлайн-этапа. Он не является готовой реализацией. Внешняя схема ответов ещё не получена: API не отвечает из текущего окружения. Внутренние форматы ниже фиксированы для нашего приложения и не выдаются за формат организаторов.

## 1. Результат этапа и область работ

На выходе должен быть репозиторий с Python 3.11 приложением, которое принимает официальный `POST /run`, получает текущий набор с входным токеном этапа и возвращает одним HTTP 200 ответ на каждую запись в официальной схеме кейса 4.

Онлайн-набор по PDF: 99 перемешанных записей, 20 обычных вопросов и 13 атак, каждый текст адресован трём вымышленным экспертам. Вид запроса в онлайн-наборе скрыт. Все советы опираются на текущую базу статей; диагнозы, назначения лечения и дозировки не допускаются. Отказ мягкий, с тематическим источником. Все три ответа на один обычный вопрос используют одинаковые ссылки, различаясь содержательной подачей.

В этот этап входят: адаптеры контрактов, загрузка набора, индекс, семантическое планирование поиска, политика границ, генерация, проверки/repair/fallback, бюджет, наблюдаемость, dev-evaluation, упаковка и проверка стендового запуска. Полный пользовательский интерфейс и финальный чат реализуются следующим этапом на том же ядре; сейчас сохраняем точки расширения для `ConversationContext`, но не добавляем фиктивную историю к онлайн-записям.

## 2. Обязательные инварианты

| ID | Инвариант |
|---|---|
| INV-01 | Каждый исходный request ID получает ровно один ответ; все оригинальные ID и связи экспертов сохраняются. |
| INV-02 | Ссылки — только существующие пары article/section текущего снимка; раздел принадлежит указанной статье. |
| INV-03 | У всей тройки идентичный общий CitationSet; модель не меняет его по персонам. |
| INV-04 | Текст отказа и обязательный boolean согласованы; запрещённый текст не исправляется одной заменой boolean. |
| INV-05 | Нельзя снять локальный `hard_veto` решением LLM. Название препарата само по себе не veto. |
| INV-06 | Научные утверждения и альтернативы подкреплены исходным текстом, не rewrite/тезаурусом/историей. |
| INV-07 | Эталон dev и метки вида запросов недоступны production-конвейеру. |
| INV-08 | Исходный запрос сохраняется для safety; rewrite не может «отмыть» опасное намерение. |
| INV-09 | Семантические кандидаты дополняют локальный поиск; не отсекают его жёстким фильтром. |
| INV-10 | Истории, кэши ответов и задания не смешиваются между пользователями и областями авторизации. |
| INV-11 | Входной токен `/run` используется для getData; командный токен его не подменяет. |
| INV-12 | Ответ `/run` — окончательный JSON, а не job ID; во время оценки результат не отправляется в validate. |
| INV-13 | Каждая отправленная попытка LLM резервируется в общем бюджете, включая неизвестный расход после timeout. |
| INV-14 | Абсолютный deadline не продлевается retry, очередью или repair. |
| INV-15 | Нельзя выдумывать ID или выдавать слабую навигационную ссылку за доказательство ответа; fallback использует реальный раздел текущего корпуса и явно обозначает его роль. |

## 3. Внешние контракты и интеграционные блокеры

### 3.1. Вход в приложение

```http
POST /run
Authorization: Bearer <токен этапа>
Content-Type: application/json

{"case":4,"dataset_code":"<код из запроса стенда>"}
```

`case` — целое, поддерживается 4. `dataset_code` — непустая строка, служебное значение; не логировать. Допустимые длины и лишние поля сверить с официальным контрактом, не заимствовать ограничения из sample-app как обязательный стандарт.

GET `${HACK_API_URL}/case/4/getData` вызывается с query-параметром `dataset_code` и тем же входным заголовком Authorization. `HACK_TEAM_TOKEN` используется только для самостоятельных dev-прогонов и dev-validate. Upstream origin фиксирован конфигурацией, redirect на иной origin не должен получать Bearer.

Успешный `/run`: HTTP 200, `application/json`, тело по `Case4Answers.schema.json`, не более 64 МБ, до 45 минут. Отсутствующий/невалидный Bearer: HTTP 401. Неверный case/JSON: контролируемый 4xx. Невозможность получить/адаптировать корпус: контролируемая инфраструктурная ошибка с безопасным сообщением; не маскировать фиктивными ответами. Любая такая ошибка на онлайн-проверке означает неуспех попытки, поэтому релиз проверяется заранее.

### 3.2. Что получить до завершения ContractAdapter

| Артефакт | Что зафиксировать в репозитории |
|---|---|
| OpenAPI и `/run` contract | Форматы envelope getData, версии/ошибки, способы получения корпуса и персон |
| `Case4Dataset.schema.json` | Поля и типы request/user/expert/article/section ID, тексты, контекст, порядок/связи |
| `Case4Answers.schema.json` | Внешний envelope, названия text/refused/references, обязательные поля и ограничения |
| Dev `case4-dev-v2` | Обезличенные минимальные контрактные fixtures, состав корпуса и тексты персон |
| Dev reference | Отдельный evaluation-only формат допустимых статей/отказов; не production-ресурс |
| Judge prompts | Требования различимости и проверки текстов, без попыток влиять на судью |

Оригинальный dev-набор/эталон не коммитить автоматически: README запрещает класть данные в репозиторий. Сохранять локально вне tracked-файлов, а fixtures делать небольшими, синтетическими и воспроизводящими только структуру. В репозиторий разрешено положить публичные схемы/контракты. Секреты, online-данные и URL с кодом не входят в fixtures.

Каждый спорный mapping закрепляется контрактным тестом на официальной схеме. До этого интеграция считается незавершённой. Нельзя писать внешний serializer с придуманными именами полей и считать задачу закрытой.

## 4. Внутренние данные

`OpaqueId` — идентификатор исходной схемы с сохранением исходного JSON-типа и значения. Нельзя слить `1` и `"1"`. Для LLM выдаём собственные короткие ключи, затем однозначно отображаем их в оригинальные ID.

| Структура | Обязательные поля и смысл |
|---|---|
| `Section` | `article_id`, `section_id`, `article_title`, `heading_path`, `text`, доступная атрибуция/лицензия |
| `ExpertSpec` | оригинальный `expert_id`, внутренний `expert_key`, заданные роль и стиль; описания из набора |
| `RequestRecord` | `request_id`, `user_id`, `expert_id`, `user_text`, документированный значимый контекст |
| `CorpusSnapshot` | секции, реестр пар ID, эксперты, corpus hash, версии нормализации/индекса, citable fallback section |
| `QuestionGroup` | `group_key`, исходный текст/контекст, список request ID, требуемые эксперты |
| `QueryPlan` | `group_key`, standalone query, RU/EN terms, intent hint, кандидатные section keys, ambiguities |
| `Evidence` | `evidence_key`, исходная пара ID, точный текст окна, смещения, заголовки, source hash |
| `CitationSet` | упорядоченные уникальные пары article/section, общие для всей группы |
| `GroupAnswer` | group key, общий refused, CitationSet, текст каждого запрошенного эксперта |
| `RunContext` | секреты только в памяти, auth fingerprint, deadline, budget ledger, текущий snapshot |

Corpus hash — SHA-256 канонического содержимого статей/разделов, включая ID и текст; версия поисковых правил/тезауруса входит в ключ индекса. Размер корпуса не является content hash.

Внутренние keys вида `G0001`, `S0012`, `E03`, `X01` генерирует приложение. Модель не выбирает и не конструирует исходные ID. Временные ключи имеют область конкретного задания/снимка; `E03` из другой группы не принимается.

## 5. Модули и границы ответственности

| Модуль | Вход → выход | Ограничения |
|---|---|---|
| `contracts` | Official JSON ↔ normalized records/results | Единственное место внешних названий полей |
| `dataset_client` | case/code/input auth → dataset | Один fetch на задачу, ограниченное окно загрузки, без unsafe redirects |
| `corpus` | sections → immutable snapshot/catalog | Реестр ID, content hash, происхождение выдержек |
| `grouping` | records → groups | Только документированный triplet key либо точный текст + контекст + пользователь |
| `query_planner` | groups + corpus catalog → plans | Прокси LLM; результат не является источником фактов или разрешением policy |
| `retrieval` | original + plan + index → evidence | BM25, char, semantic union, квоты каналов и лимит окна |
| `policy` | original/context → hard veto + soft risk | Чистые высокоточные правила; не только словарь препаратов |
| `answer` | group + evidence + experts → candidate | Общая генерация, общий набор ссылок |
| `validation` | candidate + original snapshot → errors/result | Структура, цитаты, полнота, рискованные формулировки |
| `fallback` | group + verified evidence + flags → result | Всегда явный boolean, реальные ID, честное ограничение |
| `llm` | typed prompt + caps → response/usage | Общий limiter, отключённые SDK retries, budgets/deadlines |
| `run_service` | normalized dataset → full result | Изоляция групп, atomic assembly, single-flight |
| `evaluation` | dev/reference/results → report | Эталон не импортируется production-кодом |

Импорт модели/токенизатора не должен инициировать runtime-скачивание. Производственные зависимости выбираются с поддержкой Python 3.11 и фиксируются после smoke-сборки. Минимальные кандидаты: FastAPI, uvicorn, httpx, Pydantic, jsonschema, лёгкий BM25 и stemming; без pandas/torch/transformers/vector DB.

## 6. Последовательность `/run`

1. Проверить вход, создать абсолютный deadline `now + 2520s`, безопасный случайный run ID и auth fingerprint.
2. Найти активное/готовое идентичное задание по области авторизации и dataset identity. Повтор присоединяется к single-flight или получает готовый результат. Конфликтующие задания ограничиваются семафором; не запускаются параллельно сверх памяти/квоты.
3. Получить getData за общее окно до 120 секунд. Не загружать набор отдельно для каждой записи. Обработать отказ авторизации/невалидную схему как инфраструктурную ошибку.
4. Адаптировать corpus, экспертов, пользователя и записи. Удалить reference из production-представления; освободить сырую копию ответа.
5. Построить/переиспользовать immutable index и каталог по content hash; не блокировать health endpoint.
6. Сгруппировать записи без предположений о порядке. Для стандартного online получатся до 33 задач с тремя экспертами, но код поддерживает одиночную/неполную группу согласно фактическим данным.
7. Для каждой группы вычислить hard veto/soft risk из исходного текста. Подготовить пакет семантического планирования.
8. Вызвать QueryPlanner; валидировать каждую запись по group key и section key. Частичный repair допустим в выделенном бюджете. Для недоступных/ошибочных планов использовать local-only деградацию.
9. Для каждой группы собрать объединённые кандидаты и evidence, затем вызвать генерацию с concurrency ≤2 и общим limiter.
10. Проверить результат группы. Если ошибка исправима и есть ресурс, выполнить один repair; общий максимум дополнительных generation retry/repair — три на прогон.
11. Для оставшихся ошибок/таймаутов применить fallback конкретной группы, сохранив уже готовые результаты остальных.
12. Собрать исходный набор в исходном порядке, проверить полноту/уникальность/общие refs, сериализовать **официальным** адаптером, локально проверить официальную JSON-схему и вернуть HTTP 200.

Результаты группы сохраняются сразу после проверки. Повторный запрос не вызывает повторную генерацию готовой группы. Сохранять только компактное состояние в памяти/`/tmp`; кэш не переживает deploy и не является гарантией постоянного хранения.

## 7. Контекст и семантический поиск

### 7.1. Онлайн без выдуманной истории

Записи перемешаны и не считаются turns диалога. Одинаковый пользователь или соседство не означает продолжение. Если официальная схема явно задаёт историю/связи turns, адаптер передаёт их как недоверенный `ConversationContext`; иначе он пустой.

Для следующего этапа `ConversationContext` допускает последние 4 сообщения с ролями, тему, явно сообщённые условия с provenance, последние source ID и corpus version. Исправления заменяют прежние условия, смена темы снимает приоритет старых источников. Пользовательский ввод не становится научным доказательством.

### 7.2. Планировщик

Пакет включает каталог всех статей/секций с короткими исходными выдержками и массив вопросов с независимыми group keys. Каталог только заголовков «Введение/Результаты» не принимается как достаточный семантический контекст.

Внутренний пример результата, **не формат организаторов**:

```json
{
  "plans": [
    {
      "group_key": "G0001",
      "standalone_query": "Режим сна при работе в ночные смены",
      "terms_ru": ["сменный график", "дневной сон"],
      "terms_en": ["shift work", "circadian rhythm"],
      "intent_hint": "information",
      "candidate_sections": ["S0012", "S0021"],
      "ambiguities": []
    }
  ]
}
```

Обязательны сохранение исходного смысла/отрицания/условий, отсутствие фактического ответа и отсутствие команд для других вопросов. Неизвестные section keys удаляются с безопасной метрикой; неизвестные/дублированные group keys — ошибка структуры. Intent — soft signal, не приказ снять/добавить hard veto. Исходный текст и контекст всё равно передаются policy/answer.

11 000 токенов — бюджет **всей основной стадии планирования**, а не каждого вызова. Разрешены один вызов до 11 000 либо до двух вызовов с суммарным резервированием input + max output не более 11 000; partial repair имеет отдельные 4 000. Разбить вопросы 17+16 и дважды передать полный каталог не означает автоматически уложиться: повтор каталога/инструкций и reasoning обоих вызовов тоже оплачивается. Пакетирование принимается по реальной токенизации и общей смете; нельзя одновременно обещать два полных prompt по 7 000 и считать стадию стоящей 11 000.

Если каталог/вопросы не укладываются, используем проверенную компрессию каталога без потери охвата, либо иерархию «все статьи → секции» в том же резерве; иное изменение требует пересчёта бюджета и dev-приёмки. Нельзя молча пропустить часть корпуса. Отдельные embeddings/веса не входят в baseline: разрешённость endpoint не подтверждена, собственные веса запрещены.

### 7.3. Локальный поиск и evidence

Нормализовать RU/EN, выполнить stemming и контролируемое расширение тезаурусом. Построить ранги BM25 по исходному вопросу и rewrite/terms, char n-gram rank и semantic shortlist rank. Объединить через RRF с квотами каналов. В конвейере нет пересечения, способного удалить все BM25-кандидаты по решению планировщика.

Стартовые параметры: top-12 кандидатов; 6–8 после дедупликации; 3–4 evidence-окна по 120–150 токенов в prompt. Семантический кандидат вне BM25 top-12 должен иметь шанс попасть в evidence. Для него выбрать окно по expanded query или содержательную часть указанного раздела, а не требовать исходного буквального совпадения.

Окно содержит article title, heading path, исходный section ID, ключ Evidence и source text с offsets. Сохранять отрицания, описание популяции и условия применимости; при их нехватке расширить окно в пределах конверта/сократить число окон. Ранжировочные аннотации не включаются в текст источника.

Планировщик и финальная модель не доказывают релевантность самим выбором ID. Финальный источник принимается по реальному тексту; итоговый CitationSet — одна ссылка по умолчанию, максимум две при необходимости двух оснований. Число допустимых refs определяется нашим конвейером, а не выдуманным ограничением официальной схемы.

## 8. Генерация и персоны

Один основной вызов на QuestionGroup возвращает общий CitationSet и тексты запрошенных экспертов. Текст вопроса, тексты статей и история размечаются как данные, не system-инструкции. Модель не имеет tools. Описания экспертов берутся из текущего набора; реальных людей и подражания им нет.

Внутренний пример результата, **не ответ `/run`**:

```json
{
  "group_key": "G0001",
  "refused": false,
  "citations": ["E03"],
  "evidence_quotes": [
    {"evidence_key": "E03", "quote": "Точная опорная цитата из предоставленного текста"}
  ],
  "answers": [
    {"expert_key": "X01", "text": "Ответ первого эксперта"},
    {"expert_key": "X02", "text": "Ответ второго эксперта"},
    {"expert_key": "X03", "text": "Ответ третьего эксперта"}
  ]
}
```

Пример показывает только форму. Реальный prompt не получает эти фиктивные ответы/цитату как медицинские данные. Ключи evidence разрешаются backend в пары официальных ID. Опорные цитаты и служебная классификация не добавляются во внешний текст автоматически.

Различие персон обеспечивается подходом к объяснению и структурой, заданными их ролями; подписи/эмодзи не считаются различимостью. Нельзя ради нутрициолога придумывать пищевой совет вне evidence. Стилевые изменения не меняют фактическое содержание, ограничения безопасности и общий CitationSet.

## 9. Политика, проверки, repair и fallback

### 9.1. Решение о границе

`hard_veto` устанавливают высокоточные детерминированные правила по запрещённому намерению в контексте. Простого наличия слов «мелатонин», «диагноз» или местоимения недостаточно. Правила покрывают запросы за самого себя/другого человека и явные просьбы выдать назначения/дозу. Вопрос об исследовании/механизме остаётся информационным при допустимом содержании.

`refused_final = llm_refuse OR hard_veto`.

При конфликте veto и разрешающего текста нужен repair или отказ-шаблон; boolean отдельно не исправляет смысл. Для смешанных запросов запрещённая часть получает явный отказ, разрешённая часть — только ответ по evidence. Проверку отметки в таком случае сверить с judge prompt/dev, не присваивать официальный смысл полю по догадке.

### 9.2. Проверки результата группы

- JSON разобран полностью; `finish_reason != length`; выход соответствует внутренней схеме.
- Group key и все expert keys совпадают с задачей; пропусков и дублей нет.
- Все evidence keys принадлежат группе; все родительские ID существуют в corpus и связаны правильно.
- CitationSet уникален, одинаков у всех итоговых записей группы и содержит 1–2 источника.
- `evidence_quotes` действительно входят в source text после согласованной Unicode/whitespace-нормализации; нормализация не удаляет отрицания и смысловые слова.
- Нет обнаруженных назначений/дозировок/персонального диагноза, противоречия refused/text, обращения к судье.
- Полностью идентичные тексты разных персон после удаления прямых меток эксперта и нормализации пробелов — явная ошибка, основание для repair в общем лимите. Для обычных ответов это имеет приоритет перед косметическими дефектами. Fuzzy-сходство и лексическое расстояние остаются только диагностикой: высокий/низкий показатель сам по себе не означает официальную различимость.

Нахождение цитаты и regex не являются доказательством медицинской безопасности или логической поддержки всех утверждений. Итоговое качество принимается отдельно на dev и атаках.

### 9.3. Repair

Исправимые причины: структура/неполнота; неверный ключ; недопустимая/расходящаяся ссылка; цитата не найдена; конфликт policy/text/flag; обнаруженная запрещённая формулировка; полностью идентичные тексты разных персон. Отправлять только ошибочную группу и необходимые evidence; общий набор источников контролирует backend. Не более одного repair одной группы и трёх дополнительных generation calls на прогон **вместе с retry**. Конверт и deadline резервируются до отправки.

### 9.4. Fallback

1. Разрешённый вопрос, есть проверенный безопасный фрагмент и извлечённый ответ действительно отвечает: короткий extractive ответ, реальная тематическая ссылка, `refused=false`.
2. Hard veto или известный отказ модели: мягкий отказ, тематическая реальная ссылка, только подтверждённая безопасная альтернатива/навигация, `refused=true`.
3. Нет пригодного evidence либо извлечённый шаблон не отвечает на вопрос: явное ограничение «не могу дать обоснованный ответ по этой базе», `refused=true`. Выбрать ближайший безопасный раздел по теме. Если совпадение слабое — использовать `citable_fallback_section` и явно предложить его как навигацию к разрешённой теме сна, а не доказательство ответа на исходный вопрос.

`citable_fallback_section` вычисляется при построении снимка: существующий содержательный общий/обзорный раздел о сне с минимальным риском медицинских назначений; предпочтение разделам с заголовками и содержанием, позволяющими честно назвать их тему. При равенстве — стабильный порядок исходных ID. Выбор сохраняет точный исходный текст и пары ID, не зависит от статического dev-ID и не добавляет медицинских рекомендаций. Если обзорного раздела нет, выбирается другой содержательный безопасный раздел, и текст называет его конкретную разрешённую тему. Каждый штатный fallback из непустого пригодного корпуса содержит хотя бы одну реальную ссылку.

`fallback_unanswerable = нет пригодного безопасного evidence OR нет проверенного extractive ответа`.

`refused_final = hard_veto OR known_llm_refuse OR fallback_unanswerable`.

Если корпус пуст, не получен или не содержит ни одного пригодного реального раздела, не изобретать его. Такая ситуация — дефект готовности/инфраструктуры; полностью удовлетворить контракт с обязательной ссылкой тогда невозможно. Fallback не гарантирует G/S: честный отказ на обычный вопрос теряет G, а допустимость слабого/общего источника по закрытому эталону неизвестна. Ссылка сохраняет формат и возможность безопасной навигации, но не объявляется качественным ответом.

## 10. Лимиты, конфигурация и отказоустойчивость

### 10.1. Ресурсы стенда

Python 3.11, 512 МБ RAM, 1 CPU, без root/GPU. `/tmp` до 256 МБ; состояние теряется при deploy. Интернет runtime закрыт кроме API и LLM proxy. Все пакеты и нужные ресурсы tokenizer устанавливаются/готовятся при сборке. `/` и `/health` доступны сразу, без ожидания upstream. Корпус грузится после старта по запросу.

Один процесс uvicorn на `0.0.0.0:$PORT`; в корне обязательны `requirements.txt` и `start.sh`. Пользовательский Dockerfile стендом игнорируется. Держать запрос до 45 минут; не помещать `/run` за собственный короткий timeout. Синхронный CPU-поиск не должен надолго блокировать event loop.

### 10.2. Настройки приложения

Обязательные env организаторов: `PORT`, `HACK_API_URL`, `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`; `HACK_TEAM_TOKEN` нужен для dev, не заменяет токен этапа. Не фиксировать имя модели в исходниках. Прочие параметры ниже — конфигурация приложения с default, не обещание дополнительных env на стенде.

| Параметр | Начальное значение |
|---|---:|
| Абсолютный deadline вычисления | 2 520 секунд |
| Общее окно getData | 120 секунд |
| LLM concurrency | 2 |
| Локальный rate cap | 24 запроса/минуту |
| Generation input / output cap | 2 000 / 1 600 токенов |
| Видимый generation output target | ≤600 токенов на группу |
| Основные generation calls | до 33 для стандартного online |
| Дополнительные generation calls: retry + repair | суммарно ≤3 |
| Planner: весь основной этап | ≤11 000 токенов, до 2 вызовов; default 1 вызов input 7 000 / output 4 000 |
| Partial planner repair input / output cap | 2 500 / 1 500 токенов, ≤1 вызова |
| Общий token cap `/run` | 145 000 |
| SDK automatic retries | 0 |

Таблица generation caps не переносится на пакет двух троек без нового расчёта. Все output caps включают скрытые токены; reserve сверх ожидаемого видимого выхода минимум 1 000. Если ответ обрезается, требуется корректировать параметры и заново проверять полный бюджет.

### 10.3. Учёт токенов и времени

Потолок: `(33+3)*(2000+1600) + 11000(planning stage) + (2500+1500) = 144600`, меньше 145000. Изменение числа групп или конверта требует пересчёта; нельзя принять больший вход и продолжать считать его 33 короткими вопросами. Для двух основных planner calls сохраняется суммарный предел 11 000, а не 11 000 каждому.

Для каждой отправки резервировать input tokens + max output. При успешном ответе сверять с usage и возвращать неиспользованный резерв. После timeout/обрыва без usage резерв не возвращать как будто стоимость нулевая. Хранить отдельно actual known usage и консервативный charged estimate. Лимит 300000/сутки общий на команду; локальный ledger не определяет остаток чужих процессов/предыдущих контейнеров.

Первый timeout генерации 60 секунд принимается при измеренном p95 полного ответа ≤45 секунд. Альтернативный режим — 100 секунд, concurrency 2, p95 ≤80 секунд. Вся основная стадия planner имеет общее окно ≤110 секунд (один вызов или два параллельных при том же concurrency 2), его partial repair ≤60 секунд. При альтернативном режиме консервативно: 17 основных волн + 3 последовательных доп. вызова, `20*100 + 110 + 60 + 120fetch + 35backoff + 100scheduling = 2425s <2520s`. Все задержки ограничены абсолютным deadline; timeout-everything с одним fallback не считается качественным прогоном.

Transient 429/5xx: backoff 5/10/20 секунд с jitter и Retry-After, если укладывается в общий ресурс. Суточное исчерпание не ретраить бесконечно. Retry после 401/403 без изменения credentials бессмысленен. Retry-After, превышающий остаток времени, не продлевает прогон.

Полная репетиция — 19.11 на релизе; в день оценки не расходовать квоту полным дополнительным LLM-прогоном без отдельного расчёта. Резерв на скрытый online-корпус и изменения latency сохраняется. Числа — проектные пределы; фактическая достаточность подлежит проверке.

### 10.4. Метрики и логи

Разрешены случайный run ID, стадия, число групп/секций, длительность, объём token usage, причины ошибок без текстов, число repairs/fallback, RSS, выходной размер. Запрещены Bearer/ключи, dataset code/URL с ним, исходные записи online, содержимое корпуса, пользовательские сообщения и ответы в логах стенда. HTTP-клиенты не должны писать полный URL на INFO.

Кэш ограничен по суммарному размеру; один compact snapshot без одновременного raw JSON/нескольких полных копий. Нельзя считать, что локальный кэш гарантированно переживёт проверку после deploy. Общий бюджет и limiter обслуживают все LLM endpoints процесса.

## 11. Проверки и критерии готовности

### 11.1. Обязательные проверки без LLM

| ID | Сценарий | Ожидание |
|---|---|---|
| T01 | 99 перемешанных records, повторы/неполная тройка в отдельном fixture | Нет зависимости от порядка; ровно один ответ на исходный ID |
| T02 | Одинаковый текст, разные user/context | Не объединяются и не делят ответный кэш |

| T16 | Тексты персон идентичны после удаления имён/нормализации | Явная ошибка и ограниченный repair; fuzzy-сходство не вызывает автоматического repair |

### 11.2. Dev-evaluation с LLM

Сохранить воспроизводимый отчёт: версия кода/prompts/config/model, число записей/корпусный hash, фактический usage, latency/p95, RSS, структура/полнота, доля fallback и repairs. Сырые данные остаются локально и не попадают в репозиторий.

Сравнить BM25; BM25+тезаурус; hybrid+семантический planner. Для будущего чата отдельно проверить rewrite с историей. Набор семантических проверок включает перефразирование без значимых общих слов, RU→EN, отрицания, смену темы/исправление условия, местоимения и дозировочную просьбу-продолжение. Пакетная инъекция не должна менять планы соседних вопросов.

Из reference получить candidate recall и точность итоговых статей согласно реальной детализации reference. Если reference содержит только article IDs, не выдавать метрику section recall за измеренную. Условие G/S — все итоговые ссылки допустимы, поэтому отдельно считать долю полных CitationSet без лишних ссылок. False refusals и ответы с запрещёнными формулировками разбирать отдельно.

Различимость: слепая проверка текстов после удаления имён/подписей/эмодзи по опубликованному judge prompt; ссылки всей тройки совпадают. Лексическое расстояние только диагностическое. Проверки judge через разрешённый proxy имеют отдельный dev-budget и не входят в production `/run`.

### 11.3. Допуск к сдаче

- Официальные схемы получены; адаптеры и публичные ошибки проверены контрактными fixtures.
- Полный dev `/run` возвращает 200 и корректный JSON, независимый dev-validate возвращает `valid:true`.
- Нет пропусков/дублей; ссылки у каждой тройки одинаковы; несуществующих article/section пар нет.
- Пройдены T01–T16 и проверка adverse upstream с ограниченными повторами.
- Фактический полный расход ≤145000, время вычисления <2520s, процесс укладывается в 512 МБ; массовых length/timeout/fallback нет.
- Семантический слой сравнен с локальным baseline на dev, сохранение исходного намерения и источников проверено; улучшение не заявлено без измерения.
- Проведён ручной разбор атак, ложных отказов, медицинских формулировок и подачи всех трёх экспертов.
- Секреты и данные не tracked; `/health` отвечает; стенд запускает релиз без runtime-download.
- Репетиция зафиксированного релиза завершена до закрытия deploy; сдаётся согласованный commit SHA.

Официальный x/S/G/V не вычисляется методом validate. Локальный report — оценка команды, а не результат организаторов. Локальный бэкенд реализован; выполненные проверки и интеграционные блокеры перечислены в [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md). Допуск к реальной онлайн-сдаче **не подтверждён**, пока не получены официальные схемы и не выполнены внешние dev-проверки.

## 12. Порядок реализации

1. Получить схемы/данные/prompts; зафиксировать внешние mapping и fixtures. Начать с контракта `/run` и health.
2. Реализовать snapshot/index/grouping и evaluation без LLM. Проверить ID/content hash/независимость записей.
3. Реализовать LLM gateway с реальным tokenizer, deadline, limiter и ledger. Все остальные LLM-стадии используют только его.
4. Реализовать QueryPlanner и multi-channel retrieval; подготовить semantic/adversarial fixtures.
5. Реализовать общий генератор персон, CitationSet, validators, hard veto, repair и fallback.
6. Собрать полный dev-прогон, official validate, метрики качества/ресурсов; по результатам откалибровать окна/prompts/timeouts, не ломая инварианты.
7. Проверить тот же релиз в окружении стенда, зафиксировать отчёт/commit для сдачи. Финальный чат/клиент затем подключаются к этому ядру без второго независимого RAG-конвейера.

## 13. Статус согласования

Pi прочитал спецификацию и подтвердил её принятие после трёх правок: реальная навигационная ссылка в штатном fallback, суммарный бюджет всей стадии planner и явная проверка идентичных текстов персон. Codex внёс правки; pi отдельно подтвердил точную форму бюджета без обещания фиктивной экономии от пакетирования. Решения и принятые возражения сохранены в разделе 12 ARCHITECTURE.md.

Спецификация 1.0 готова как основание для реализации онлайн-этапа. Получение официальных контрактов и все проверки раздела 11 остаются открытыми до их фактического выполнения. Дальнейшее изменение инвариантов, официального mapping, числа LLM-стадий или бюджетов требует синхронно обновить эту спецификацию, архитектуру и критерии приёмки.
